## 2. Travail réalisé dans le dépôt

- Cycle de jeu Incognito : démarrage au nombre minimal de joueurs, alias par
  manche, chat, cooldown, votes, fermeture des manches et attribution des points.
- Vote associé au premier message lorsqu’un autre joueur est présent. Le message
  et son vote sont enregistrés ensemble. Le jeu en solitaire reste possible ;
  l’arrivée d’un autre joueur rétablit l’obligation de voter avant de reparler.
- Interface : compte à rebours, alias personnel, vote courant, classement lié aux
  profils publics et résultats de chaque manche pour tous les joueurs. Un score
  de zéro est distingué d’une absence de participation à la manche.
- Bibliothèque privée de scripts : création, consultation, modification,
  suppression et réutilisation dans les réglages d’un agent. L’accès à un script
  d’un autre propriétaire est rejeté.
- Réglages Incognito propres à chaque joueur : activation, arrêt, fournisseur,
  modèle et prompt. Une révision de configuration invalide les décisions calculées
  avec d’anciens réglages. Le prompt final, script compris, est limité à 2 000 caractères.
- Fournisseurs de modèles : modèle local SmolLM2 sur CPU et API Groq. Les décisions
  sont générées dans un worker séparé ; afficher ou rafraîchir une page ne lance
  pas d’inférence. Les agents activés sont traités automatiquement par ce worker.
- Profils publics : nombres de parties jouées et gagnées, graphique quotidien
  sans bibliothèque supplémentaire et tableau des valeurs. Une partie jouée est
  comptée à la date de participation ; une victoire, à la date de fin. Une égalité
  au score final n’est pas comptée comme victoire.
- PokeClash : lecture structurée du flux, envoi par le compte serveur autorisé,
  agent configurable, exécution ponctuelle mise en file et mode automatique.
  L’affichage ne prétend pas connaître un score ou un chronomètre absent du flux.
- Tests de règles, de droits d’accès, de configuration, de concurrence logique,
  de contrats de modèles et de transport simulé. Les tests n’envoient aucun
  message réel au service PokeClash.

## 3. Validation et limites constatées

Les tests Django s’exécutent dans l’environnement virtuel existant sous Ubuntu
via WSL. Le 14 novembre 2026, la commande
`.venv/bin/python manage.py test game users helbplays agents` a réussi les
**65 tests** de la suite complète. La sous-suite interface/profils comporte 13
tests réussis. `manage.py makemigrations --check --dry-run` ne détecte aucun
changement de modèle sans migration.

**Validation sur la VM de cours : non effectuée.** Aucun envoi réel PokeClash ni
appel Groq authentifié n’est revendiqué ici. La présence d’un adaptateur et de
tests avec réponses simulées ne prouve pas le fonctionnement avec des clés réelles.
Le premier lancement local peut télécharger des poids et dépend des ressources
disponibles ; son résultat de validation est à distinguer de celui des tests simulés.

Le fichier `requirements.txt` est actuellement entièrement commenté. Le point 1
relatif aux dépendances est hors périmètre de cette intervention ; le fichier reste
en l’état. Une installation neuve via ce fichier ne suffit donc pas
encore à préparer l’application ; l’environnement de test existant contient déjà
les dépendances Django. Ce point reste à traiter avant une installation propre.

## 4. Difficultés et choix techniques à discuter

Les envois manuels et automatiques doivent partager les mêmes règles : cooldown,
vote obligatoire, propriété des scripts et contrôle du compte externe. Les
inférences s’exécutent hors transaction ; un bail et une vérification de révision
empêchent ensuite d’appliquer une décision devenue obsolète. Les erreurs utilisent
un délai progressif avant une nouvelle tentative. Un timeout d’envoi externe n’est
pas rejoué automatiquement car le service peut déjà avoir reçu le message.
